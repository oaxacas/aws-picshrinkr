# PicShrinkr – Serverless File Processing Pipeline on AWS

PicShrinkr is a serverless backend application built using AWS. It demonstrates how cloud services can automatically react to events without requiring traditional servers or a user interface. When a file is uploaded to a specific Amazon S3 bucket, an AWS Lambda function automatically processes the file by copying it to another S3 bucket and saving metadata to a DynamoDB table. All activity is logged in CloudWatch.

This project was created as a final portfolio project for an AWS computing course and demonstrates real-world use of AWS serverless services.

---

## Project Overview

### Problem

Many cloud workloads operate entirely in the background without a web interface. They react to events such as file uploads by processing data automatically. This project demonstrates how to build such a backend automation pipeline using AWS.

### Solution

PicShrinkr is a serverless backend application built using AWS. 
Whenever a file is uploaded to the “raw” S3 bucket:

1. S3 emits an object created event.
2. AWS Lambda is triggered.
3. The file is copied to a “processed” S3 bucket.
4. Metadata about the file and processing time is recorded in DynamoDB.
5. Logs are written to CloudWatch for monitoring and debugging.

---

## Architecture Overview

**Primary Compute Service**

- **AWS Lambda** – main compute service that reacts to S3 events.

**Supporting Services**

- **Amazon S3**
  - Raw uploads bucket (event source)
  - Processed bucket (output)
- **Amazon DynamoDB**
  - Stores metadata about each processed file
- **Amazon CloudWatch**
  - Logs Lambda executions and errors
- **AWS IAM**
  - Provides least-privilege roles and permissions

### Data Flow

1. A file is uploaded to the **raw uploads S3 bucket**.
2. S3 triggers the **PicShrinkr Lambda function** with an event.
3. Lambda reads the event, copies the file to the **processed S3 bucket**, and writes an item into the **PicShrinkrMetadata** DynamoDB table.
4. CloudWatch stores logs and metrics for observability.

## Implementation Details

### S3 Buckets

- **Raw Uploads Bucket** (e.g. `picshrinkr-raw-uploads-so`)  
  - Files are uploaded here manually or via tools.  
  - Configured to send `ObjectCreated` events to the Lambda function.

- **Processed Bucket** (e.g. `picshrinkr-processed-so`)  
  - Lambda copies the uploaded files into this bucket with a new key name, such as `processed-filename.ext`.

### DynamoDB Table

- **Table Name:** `PicShrinkrMetadata`  
- **Partition Key:** `imageId` (String)  

Example fields stored:

- `imageId` – unique ID generated by Lambda  
- `originalFileName` – the original file name  
- `originalBucket` – name of the raw bucket  
- `processedBucket` – name of the processed bucket  
- `originalKey` – S3 key of the raw file  
- `processedKey` – S3 key of the processed file  
- `processedAt` – timestamp when processing occurred

### Lambda Function

- **Function Name:** `PicShrinkrResizeFunction`  
- **Runtime:** Python 3.11  
- **Trigger:** S3 `ObjectCreated` event from the raw bucket  

High-level workflow:

1. Read the S3 event to get bucket and key.
2. Generate a unique `imageId` and a new processed key.
3. Use `s3.copy_object` to copy the file from the raw bucket to the processed bucket.
4. Write a metadata item into DynamoDB.
5. Log details and errors to CloudWatch.

Environment variables:

- `DEST_BUCKET` – name of the processed bucket  
- `TABLE_NAME` – name of the DynamoDB table

## Testing and Verification

To test the system:

1. Upload a file to the **raw S3 bucket**.
2. Confirm that the **processed S3 bucket** contains a file with a name like `processed-<original-file-name>`.
3. Check the **PicShrinkrMetadata** DynamoDB table to verify that a new metadata item has been created.
4. View **CloudWatch logs** to see the Lambda execution details and ensure there were no errors.

Screenshots of these steps (S3, Lambda, DynamoDB, CloudWatch) are included in the `screenshots/` folder.

## Security

- Lambda uses a dedicated IAM role with **least privilege permissions**:
  - `s3:GetObject` only on the raw bucket
  - `s3:PutObject` only on the processed bucket
  - `dynamodb:PutItem` only on the metadata table
  - CloudWatch Logs permissions for logging
- No access keys or secrets are stored in the code; security is handled via IAM roles.

## Scalability and High Availability

- **Scalability:**  
  - AWS Lambda scales automatically with the number of incoming S3 events.  
  - S3 and DynamoDB are fully managed and scale automatically based on demand.

- **High Availability:**  
  - Lambda, S3, and DynamoDB are multi AZ services, providing built in fault tolerance without extra configuration.

## Cost Optimization

- The project is designed to operate within the **AWS Free Tier** for typical test workloads.
- Only serverless, managed services are used, minimizing idle resource cost.
- After testing and documentation, resources can be deleted to avoid additional charges.
